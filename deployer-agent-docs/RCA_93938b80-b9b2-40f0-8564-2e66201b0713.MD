## How production receives STRIPE_MODE, and can a publish push 'test'?
Mechanism (per platform secrets model + the shared/single-live-slot store):
- STRIPE_MODE is a user-owned secret that already exists and is customized in production (=`live`). On every redeploy after the first, user secrets are **carried forward from the previous PRODUCTION run**; the preview `.env` only **ADDS new keys and never overwrites a key already present/customized in prod**. Preview runtime's `STRIPE_MODE=test` therefore does **not** propagate to production on publish — production keeps `live`.
- **Defense-in-depth in code:** even if `test` somehow reached prod while the live secret key stayed, server.py line 55 raises CONFIG ERROR and refuses to start unless `STRIPE_ALLOW_LIVE=1` (which is unset here). A refused boot fails the deploy health_check → no promote → the live version keeps serving. So production cannot silently flip to test.

**Conclusion:** A future publish will NOT push `test` to production under current state — the prod value is sticky (carried forward, not overwritten by preview), and the app's own boot guard blocks a test-mode-with-live-key start as a backstop. The only way prod becomes `test` is if someone explicitly edits STRIPE_MODE to `test` in the Deployment → Secrets tab AND swaps in test keys.
