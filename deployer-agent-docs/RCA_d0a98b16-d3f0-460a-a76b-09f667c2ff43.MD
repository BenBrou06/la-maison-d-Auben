# RCA — Public reviews silently dropped (admin Témoignages shows 0)

**Deployment:** auben-preview-shop (prod URL https://auben-preview-shop.emergent.host, custom domain la-maison-dauben.com)
**Active run:** d0a98b16-d3f0-460a-a76b-09f667c2ff43 (redeploy, success)
**DB inspected:** auben-preview-shop-test_database
**Mode:** strictly read-only. No deploy/write/edit performed. No PII (emails/names/review text) read or reported.

## Symptom
Owner submitted 2 reviews from the public page `/donner-mon-avis` on production; the page showed the success message, but admin → Confiance → Témoignages clients shows 0 in every status (Tous 0).

## Root cause (confirmed)
Both submissions hit the **honeypot early-return** in `backend/reviews.py::submit_review`. After the two rate-limit inserts, line 203 runs:

```
if inp.website.strip():
    return {"status": "ok"}   # piège à robots : réponse identique, rien n'est enregistré
```

When the hidden honeypot field `website` is non-empty, the endpoint returns HTTP 200 `{"status":"ok"}` **without inserting any testimonial**. This is the only 200-returning path in the handler that does not write a document, so by elimination both of the owner's submissions took it.

Proven by the combination of:
- `rate_hits` holds exactly 2 submission events (one `review` + one `review-day` pair each), and these inserts occur BEFORE the honeypot check → the request reached the endpoint and then returned early.
- `testimonials` collection does not exist (0 docs) → nothing was ever inserted.
- Backend logs show `POST /api/reviews` → **200 OK** (×2), no HTTPException/400/429, no traceback → not a validation/rate-limit rejection, so it is the honeypot 200 path (the frontend's success message is driven by this 200).

The honeypot field is rendered in `frontend/src/pages/ReviewPage.jsx` line 170 as a visually-hidden text input literally named `website` with `autoComplete="off"`, bound to form state. Browsers / password managers frequently ignore `autoComplete="off"` on a field named `website` and autofill it — producing a false-positive bot-trap trigger that silently discards a legitimate human submission.

## Suggested fix
**Code (E1) — harden the honeypot so legitimate submissions are not silently dropped by browser autofill.** Options:
- Rename the hidden field to a non-autofill-triggering name (avoid `website`/`email`/`url`), and keep it visually hidden; consider leaving it uncontrolled (no `value` binding) rather than bound to form state.
- Prevent autofill more strongly (e.g., `autoComplete="new-password"` / randomized field name per render) and/or require the field be *changed from initial* rather than merely non-empty.
- At minimum, log when the honeypot triggers so silent drops are observable instead of invisible.
