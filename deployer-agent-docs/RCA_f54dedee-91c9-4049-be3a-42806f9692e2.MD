# RCA — "Le paiement n'a pas pu démarrer" on /boutique/suivi-sportif

**Deployment:** auben-preview-shop (7010f598-9236-4eed-b47e-6e1a914d6434)
**Active run:** f54dedee-91c9-4049-be3a-42806f9692e2 (success, serving)
**Live URL:** https://auben-preview-shop.emergent.host (domains: la-maison-dauben.com, www.la-maison-dauben.com — both verified)
**Mode:** READ-ONLY diagnosis. No deploy, no data/secret/Stripe mutation, no LIVE session created.

## Problem statement
On the live site, clicking "Acheter maintenant" for product **suivi-sportif** shows "Le paiement n'a pas pu démarrer". budget-mensuel checks out fine.

## Root cause (CONFIRMED)
The production `products` document for **slug=suivi-sportif is missing the `lookup_key` and `currency` fields**. The frontend sends `lookup_key: product.lookup_key` (→ `undefined` → omitted from the JSON body), so `POST /api/payments/checkout` fails Pydantic validation with **422 "body.lookup_key Field required"**. budget-mensuel works because its document carries `lookup_key=budget_mensuel`.

## Evidence

### (1) Recent POST /api/payments/checkout — confirmed 422s
From backend logs (run f54dedee, last 24h). Status histogram for the window: 200×5, 404×44 (all `GET /health` nginx noise), 409×1, **422×6**.
- `POST /api/payments/checkout → 422 Unprocessable Entity ×2` (cluster ~2026-11-02 17:36)
- `POST /api/payments/checkout → 422 Unprocessable Entity ×4` (earlier cluster)
- `POST /api/payments/checkout → 200 OK` ×2 — each immediately preceded by `GET .../v1/prices?lookup_keys[0]=budget_mensuel` (the working product)
- `POST /api/payments/checkout → 409 Conflict` ×1
The 200s correlate with budget_mensuel lookups; the 422s are the suivi-sportif attempts where no lookup_key reached the server.

### (2) Stripe errors / the suspected KeyError — NOT present in retained logs
- No `Traceback`, no `Exception`, no `KeyError`, and no "Stripe price sync after upload failed for suivi-sportif: 'lookup_key'" line appears anywhere in the last 1440 min of logs.
- The only `error`-level lines are nginx `connect() failed (111: Connection refused) ... /health ... 127.0.0.1:8001` — benign pod-startup race (backend not yet up), not related.
- All Stripe API calls return 200. Notably at 2026-11-02 17:36:23–24 a catalog sync DID run for suivi_sportif: `GET /v1/prices?lookup_keys[0]=suivi_sportif → 200` (a Stripe price with lookup_key `suivi_sportif` already exists), followed by a price update + new price create (all 200). So **Stripe-side the suivi_sportif price exists**; the gap is purely that the DB document never persisted the `lookup_key`/`currency` fields. (The suspected upload-time KeyError, if it happened, was outside the retained log window — the doc was created 2026-09-21.)

## Fixes
1. **Code (E1)** — two parts:
   - **Persist** `lookup_key` and `currency` onto the product document whenever a product is created/uploaded/price-synced, so new products aren't shipped without them. The suivi-sportif doc proves this write path can leave the fields unset.
   - **Harden checkout** so it does not depend on a client-supplied `lookup_key`: resolve the lookup_key server-side from the product slug (the backend already queries Stripe by lookup_key), or validate and return a clear error instead of a raw 422. This removes the "undefined → 422" fragility for any product.
   (Not reproducible in an eph sandbox — needs the live DB + Stripe.)
2. **Data backfill (User / change_mongo_data)** — set `lookup_key="suivi_sportif"` (and the appropriate `currency`, e.g. `eur`) on the production suivi-sportif document so checkout works immediately. The matching Stripe price already exists (confirmed in logs), so only the DB field is missing. Re-saving the product via the admin panel would also repopulate it if the create/sync code is fixed first.

## Not the cause
- Secrets/config are correct (STRIPE_MODE=live, PUBLIC_BASE_URL correct, keys present).
- No backend crash, no Stripe API failure, no tier/infra issue. App is healthy; this is a per-product data gap surfacing as a 422.
